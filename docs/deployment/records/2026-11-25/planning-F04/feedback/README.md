## 因果判断和补验

冻结源码 `flight_executor.py` 的 `feedback`、`run` 同时检查里程计墙钟、仿真时钟是否推进、ROS 时间戳年龄、状态新鲜度和发布者所有权。`segment_mission.py` 的 `feedback` 自行执行同一个 0.5 秒里程计门限，`flight_status` 另有 0.7 秒执行器状态失联保护。本次任务直接接收到执行器 FAILED，运行记录吻合这条分支。看到 FAILED 时 ready 已恢复，说明取样时保护前提已经变化。原始报告只存统一原因，未逐项记录触发 tick 的 `clock_advanced_at`、本进程最后一个 odom 到达时刻和 `graph_at`。可以判定独立观察点确有反馈停顿，无法精确确定执行器哪一个条件先变假，也无法从这些日志区分宿主机调度、Gazebo 锁步或 ROS 消息流的具体责任。

F04-3-long 已在相同代码、场景与门限下重新到达，保留 F04-2-long 失败计数。要定位停顿起因，可在后续同配置仿真中只读记录原生 `/clock`、MAVROS 里程计、FCU 状态和扩展状态、宿主 CPU 调度压力及 Gazebo 实时因子，为每条消息加本进程单调墙钟。若仍需定位执行器内部条件，可在独立诊断版本中仅于 fail 边沿一次性记录各反馈年龄和发布者检查年龄。另在独立 ROS master 使用自造状态流分别引入 0.45 秒和 0.55 秒的里程计停顿，并单独暂停仿真钟，分别验证正常维持、触发撤销、禁止旧轨迹恢复和有反馈后允许降落。这些故障注入属于后续建议，本次未执行。保留原有门限。

同目录 `evidence.json` 保存三轮 source trace、结果、监督日志及 PX4 子日志的 SHA-256、流量统计和失败事件，`inspect_feedback.py` 可以在归档目录直接重算。该脚本只读文件并向标准输出写 JSON，无 ROS 发布和服务调用。
